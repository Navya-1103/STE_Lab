Tutorial 04 · Security

Audit code and generate reports

Use IBM Bob to create a reusable security audit skill, scan an application against OWASP ASVS requirements, and generate SARIF and OSCAL reports that developers and AI agents can act on.

Overview & Scenario

What you will build

The Galaxium Travels application has grown into a complex codebase. A full manual security review is time-consuming and inconsistent across team members. In this tutorial you use IBM Bob to create a repeatable process that produces structured output developers can act on immediately and that can feed into an automated remediation pipeline.

What you produce

SARIF report (security/audit-results.sarif) — Machine-readable findings compatible with IDEs, GitHub Advanced Security, and CI/CD pipelines.
OSCAL POA&M (security/poam.json) — Structured remediation map that an AI agent can use to work through fixes systematically.

This tutorial audits against OWASP ASVS Level 1 controls in four categories:

V4.1.3Users can only access their own resources (access control)
V4.1.5Access control denies by default — unauthenticated requests rejected
V4.2.1IDOR protection — sensitive resources not accessible via predictable object IDs
V5.1.1All string inputs have defined maximum length constraints
V13.1.3API endpoints do not accept credentials or PII in URL query parameters
V14.4.1HTTP responses include Content-Security-Policy, X-Frame-Options, X-Content-Type-Options
V14.5.3CORS origin validated against an explicit allowlist — no wildcard origins
Prerequisites

What you need

  • IBM Bob IDE v2.x or later.
  • Git to clone the example repository.
Step 01

Set up the lab

bash
git clone https://github.com/Navya-1103/galaxium-travels
  1. Click File → Open Folder and open the galaxium-travels directory.
  2. Open the Bob chat interface (⌥⌘B Mac / Ctrl+Alt+B Windows).
  3. Run /init to initialize the development environment and create the AGENTS.md files.
bob chat
/init

Click Approve todo tools for task if prompted.

Step 02

Create an audit skill

A skill is a reusable instruction set that Bob follows to work through a specific task. You create a skill that audits the codebase against the OWASP ASVS controls listed above.

Open skill settings

  1. Under the chat interface, click Bob Settings.
  2. Click Skills in the left sidebar.
  3. Click the + button to create a new skill.

Fill in skill details

FieldValue
Skill Nameasvs-audit
DescriptionAudits a codebase against OWASP ASVS Level 1 access control, input validation, API security, and configuration requirements.
Allow Bob to use this skillToggle ON — Bob can activate the skill automatically when a plan calls for it
Scope & Locationgalaxium-travels — saves to .bob/skills/, version-controlled with the codebase

Skill instructions

Paste the following into the Skill Instructions textbox:

SKILL.md — asvs-audit
--- name: asvs-audit description: Audit a codebase against OWASP ASVS Level 1 access control, input validation, API security, and configuration requirements and produce structured findings ready for SARIF and OSCAL export. user-invocable: true --- Perform a structured security audit of this codebase. Work through the following phases in order. Do not skip phases or combine them. ## Phase 1: Discover Read and understand the application before auditing. Focus on: - Entry points: main files, route definitions, controllers - Authentication and session handling code - Input validation and sanitization code - Database query code - Any files flagged as high-risk in earlier analysis Summarize what you find before proceeding to Phase 2. ## Phase 2: Audit Check each control below. For each one record: PASS, FAIL, or N/A. For every FAIL, record the file path and line number. ### V4.1 General Access Control - V4.1.3 — Users can only access their own resources; other users' data is not accessible - V4.1.5 — Access control denies by default — unauthenticated requests are rejected ### V4.2 Operation Level Access Control - V4.2.1 — Sensitive resources cannot be accessed by manipulating a predictable object ID (IDOR protection) ### V5.1 Input Validation - V5.1.1 — All string inputs have defined maximum length constraints ### V13.1 Generic Web Service Security - V13.1.3 — API endpoints do not accept credentials or PII in URL query parameters ### V14.4 HTTP Security Headers - V14.4.1 — HTTP responses include appropriate security headers such as Content-Security-Policy, X-Frame-Options, and X-Content-Type-Options ### V14.5 HTTP Request Header Validation - V14.5.3 — CORS origin is validated against an explicit allowlist — wildcard origins are not permitted ## Phase 3: Generate Findings For each FAIL, produce a finding in this format: **Finding [N]:** - Rule: ASVS [control number] - Severity: Critical / High / Medium / Low - File: [path] - Line: [number or range, if identifiable] - Issue: [one sentence describing what was found] - Fix: [one sentence describing the recommended change] ## Phase 4: Summary Produce a short summary: - Total controls checked - Pass / Fail / N/A counts - Two-sentence overall security posture assessment Save the findings to the location specified by the plan or prompt that invoked this skill. Do not generate SARIF, OSCAL, or other report files — report generation is a separate task. Report that the audit is complete and wait for the next instruction.

Click Create to save the skill.

Step 03

Find high-risk areas to audit

Before running the full audit, ask Bob to identify the files and folders most relevant to security. This saves tokens by focusing the audit on the highest-risk areas.

Switch to Ask mode (click the mode selector or type /ask).

bob prompt — Ask mode
Explore this codebase as a Senior Security Analyst. Give me a short summary covering: 1. The primary tech stack and framework 2. Identify the files and folders most relevant to security Make sure to also review: 1. How authentication and session management are handled 2. How user input is accepted and validated 3. Where database queries are made 4. Any API endpoints that accept external input I want to understand the highest security risk areas before running an audit.

Bob reads the files and responds with a summary of the application's security surface area.

Step 04

Create a plan for auditing the high-risk areas

Switch to Plan mode (click the mode selector or type /plan).

bob prompt — Plan mode
Create a plan for auditing the high-risk areas found in the previous exploration. When auditing, use the asvs-audit skill to guide the process. When the plan runs, create the security/ directory if it does not exist and save the findings to security/audit-findings.md Save the plan to plan/audit-plan.md

Bob may ask follow-up questions to clarify the scope. Answer them or tell Bob to use its best recommendation. Click Approve todo tools for task if prompted.

Open the generated plan file to understand the audit approach before running it.

Step 05

Run the audit

Click + to start a new task, then switch to Agent mode. Set the following permissions in the chat panel:

PermissionStateWhy
Read✅ OnBob reads the codebase, the audit plan, and the skill
Edit✅ OnBob writes findings to security/audit-findings.md
Execute✅ OnBob may run shell commands to resolve paths or confirm file structure
Skill✅ OnThe audit plan invokes the asvs-audit skill
MCP❌ OffNot needed for local code analysis
bob prompt — Agent mode
Implement the @plan/audit-plan.md

Review the findings in security/audit-findings.md when the audit is complete. Saving the findings lets you start a fresh context window for report generation without re-reading the entire codebase.

Large codebases

If you exceed the context window while auditing, try auditing one ASVS category at a time — run V4 first, then V5, V13, and V14 — and ask Bob to consolidate findings at the end.

Step 06

Generate a SARIF report

SARIF is the standard interchange format for static analysis results. IDEs including Bob, GitHub Advanced Security, and most CI/CD pipelines can consume SARIF files directly.

Click + to start a new task. Switch to Agent mode and set permissions:

PermissionStateWhy
Read✅ OnBob reads findings in security/audit-findings.md
Edit✅ OnBob writes the SARIF report to the security/ directory
Execute✅ OnBob may run shell commands to resolve paths
Skill❌ OffThe skill already created the findings; not needed for report generation
MCP❌ OffNot needed for local analysis
bob prompt — Agent mode
@security/audit-findings.md Generate a SARIF 2.1.0 report from the audit findings. Save it to `security/audit-results.sarif`. Include: - Tool name: "ASVS Security Audit" - A rule entry for each ASVS control that was checked, with the control ID and description - A result entry for each finding, with severity level, file path, line number, and the fix recommendation in the message field

Bob generates security/audit-results.sarif. Confirm the file contains a runs array with results entries — one per finding.

Severity mapping

Bob maps severity as: Critical/High → SARIF error; Medium/Low → SARIF warning. The message.text for each result contains the full issue description and fix recommendation inline — so tooling like GitHub Code Scanning surfaces the remediation guidance directly in the UI.

Step 07

Generate an OSCAL remediation plan (POA&M)

The OSCAL Plan of Action and Milestones (POA&M) is a machine-readable JSON document that maps each finding to a structured remediation task with risk information, implementation guidance, and milestone assignments. Bob can read this file as a work queue — it works through each item, applies fixes, and marks milestones complete as it goes.

Click + to start a new task. Switch to Agent mode with the same Read/Edit/Execute permissions as the SARIF step.

bob prompt — Agent mode
@security/audit-findings.md Generate an OSCAL Plan of Action and Milestones (POA&M) from the audit findings. Save it to `security/poam.json`. For each finding include: - A unique UUID - The ASVS control ID as the finding reference - Severity and a one-sentence risk description - A concrete remediation task with enough detail for an AI agent to implement it without additional context — include file path, line reference, and the specific change required - A milestone label based on severity: Critical and High findings get "sprint-1", Medium and Low get "sprint-2" Use OSCAL version 1.1.2 structure.

Bob generates security/poam.json. Each poam-item contains props (severity, ASVS control, milestone), risks[], remediations[], and tasks[] — with concrete, AI-actionable implementation details.

You now have two artifacts

security/audit-results.sarif — structured findings for developer tooling and CI/CD integration.
security/poam.json — a remediation work queue for AI-assisted or human-driven remediation.

Step 08

Review findings and prioritize

Click + to start a new task. Switch to Ask mode.

bob prompt — Ask mode
@security/poam.json Review this remediation plan and identify the 3 most critical items to fix first. For each one include: - What the vulnerability is and why it is the highest priority - Which file and line to look at - What the fix involves and roughly how long it would take a developer to implement

Bob reads the POA&M and returns a prioritized summary similar to:

Example findings — Galaxium Travels

#1 — No authentication on any endpoint (V4.1.5 · Critical)
Zero authentication means any anonymous caller can execute all booking operations. This is the foundational flaw that makes every other vulnerability worse. Effort: 2–4 h.

#2 — Wildcard CORS origin (V14.5.3 · High)
Any origin can make credentialed requests to the API. Effort: 30 min.

#3 — PII in URL query parameters on GET /user (V13.1.3 · High)
Email addresses appear in GET query strings, silently leaking into server logs, proxy logs, and browser history. Effort: 1–2 h.

Business Value

Traditional approach vs. IBM Bob

Security audits are expensive, infrequent, and their findings are often too abstract for developers to act on immediately. A Bob-driven audit changes the economics entirely.

Traditional approach
  • Engage a security consultant for a manual OWASP review — typically 3–5 days and thousands in fees
  • Findings delivered as a PDF report — no machine-readable format, no CI/CD integration
  • Remediation tasks must be manually extracted and entered into a project tracker
  • Repeating the audit next quarter requires the same cost and effort
3–5 days + consultant fees, per audit cycle
With IBM Bob
  • Bob runs the full ASVS audit using a reusable skill — repeatable any time at zero incremental cost
  • Outputs SARIF (IDE and GitHub Code Scanning ready) and OSCAL POA&M (AI-actionable remediation queue)
  • Bob can immediately begin fixing sprint-1 findings from the same POA&M file
  • Skill is version-controlled — update the controls once, re-audit the whole team's repos
Under 1 hour, fully automated and repeatable
Time saved: days of manual security review per release cycle. Machine-readable output means findings go straight into developer tooling — no translation layer needed.
