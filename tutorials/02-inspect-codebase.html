Tutorial 02 · Codebase Exploration

Inspect an unfamiliar codebase

Use IBM Bob to rapidly understand an unfamiliar application — its purpose, project structure, architecture, tech stack, key components, test coverage, and deployment model — without relying on outdated documentation or waiting for teammates.

Overview

What you will learn

Getting productive in an unfamiliar codebase typically means hours of reading code, looking for documentation, and asking teammates for context. In this tutorial, you use Bob in Ask mode to systematically interrogate the Galaxium Travels codebase and extract a complete picture of the application.

You then switch to Agent mode to save everything Bob discovered into a persistent Markdown reference that your whole team can use.

Galaxium Travels is an intentionally complex, real-world-style application with a React frontend, a Python FastAPI backend, and a Java Spring Boot inventory hold service — making it a strong candidate for this workflow.

Key features you learn

Ask mode — Explore and analyze code without Bob modifying any files.
Agent mode — Let Bob write files to persist generated artifacts.
Context mentions (@) — Reference specific files/folders to give Bob precise scope.
/init — Initialize project context before asking questions.

Prerequisites

What you need

  • Bob IDE installed.
  • Git installed locally.
  • Familiarity with the basics of Bob. If new, complete the Quickstart first.
Note — different branch

This tutorial uses the default branch of Galaxium Travels (not bob-learning-path-branch). The default branch contains the full multi-service architecture needed for the exploration prompts.

Step 01

Set up your workspace

Clone the repository

bash
git clone https://github.com/IBM/galaxium-travels

Open the project in Bob IDE

  1. Launch IBM Bob IDE.
  2. Click File → Open Folder and open the galaxium-travels directory.
  3. If Bob asks "Do you trust the authors?", click Yes, I trust the authors.
  4. Open the Bob chat interface: click the Bob icon or press ⌥⌘B (Mac) / Ctrl+Alt+B (Windows).

Initialize project context

Bob defaults to Agent mode on startup. Before switching modes, run /init so Bob reads the project and generates the AGENTS.md context files it uses in subsequent interactions.

bob chat
/init

If auto-approval is disabled, Bob asks permission to read files and write the AGENTS.md files. Approve each request. Bob creates a root-level AGENTS.md and a .bob/ folder with mode-specific configuration.

Review the generated AGENTS.md to confirm that Bob correctly identified the multi-service structure of the repository.

Step 02

Switch to Ask mode

Select Ask in the mode selector below the chat input field, or type /ask to switch modes.

Ask mode is read-only

Ask mode is strictly read-only. Bob analyzes files but cannot create or modify anything, making it the right mode for all the exploration work in this tutorial.

Step 03

Understand the application purpose and project structure

Start with the broadest question: what does this application do, and how is the codebase organized? Bob reads the project structure and key files (README.md, package.json, requirements.txt, build files) and synthesizes a concise summary.

bob prompt — Ask mode
What is the purpose of this application? Describe the project structure, the high-level architecture, and the main responsibilities of each top-level directory.

Bob reads the file tree and key entry points, then produces output that includes:

  • Application purpose
  • Top-level directory responsibilities
  • A synopsis of each top-level directory's contents
  • High-level architecture diagram
Step 04

Analyze the tech stack

With the high-level structure clear, drill into the exact technologies in use. This is useful when you need to understand build tooling, evaluate dependency choices, or assess upgrade scope.

bob prompt — Ask mode
Analyze the tech stack for the entire application. For each service, list the programming language, runtime version requirements, framework, key libraries, database, and build/test tooling.

Bob inspects the dependency and configuration files for each service and produces:

  • Detailed tech stack analysis for each service
  • End-to-end testing framework identification
  • Additional tooling from the CI/CD stack and deployment scripts
  • A "Stack at a Glance" diagram that visually summarizes the tech stack across all services and layers
Step 05

Map the key components

Understanding the tech stack tells you what a codebase uses; understanding the key components tells you how it works. Use context mentions (@) to point Bob at the most relevant files and trace component boundaries across all three services.

bob prompt — Ask mode
Identify the key components of this application and explain how they interact. Reference @booking_system_frontend/src/services, @booking_system_backend/server.py, @booking_system_backend/services, @booking_system_backend/models.py, and @booking_system_inventory_hold_service/src/main/java/com/galaxium/holdservice. Describe the component responsibilities, the data flow for the booking lifecycle, and any cross-service contracts I need to know before modifying the codebase.

Bob traces the interaction chain and produces:

  • Frontend, backend API, database layer, and Java hold service component responsibilities
  • A diagram breakdown of the two booking lifecycle flows with component interactions annotated
  • A summary of the five cross-service contracts you must know before making changes
  • A component interaction map
Step 06

Assess unit test coverage

Before adding features or refactoring, know what the existing test suite covers and where the gaps are. This prompt asks Bob to read the test files and produce a coverage assessment without running the tests.

bob prompt — Ask mode
Analyze the unit test suites across all three services. Reference @booking_system_backend/tests, @booking_system_inventory_hold_service/src/test, and @booking_system_frontend/src. For each service, describe what is tested, which testing framework is used, what the test structure looks like, and identify any obvious gaps where critical logic appears to be untested.

Bob reads the test files and produces a detailed test suite analysis including:

  • Testing framework, classes under test, number of tests per class, and what is verified per class for each service
  • Critical gaps in testing
  • Missing test coverage for critical business logic
Step 07

Assess integration and end-to-end test coverage

Unit tests tell you whether individual components work in isolation; integration and end-to-end tests tell you whether the services work correctly together. This is particularly important for Galaxium Travels because the booking confirmation flow spans all three services.

bob prompt — Ask mode
Analyze the end-to-end and integration test coverage. Reference @tests_e2e and any cross-service test fixtures you can identify. Describe which cross-service flows are covered, which are not, what test infrastructure is required to run the suite, and what the tests assert at the boundary level.

Bob reads the end-to-end test suite and generates detailed analysis including:

  • Test infrastructure and requirements to run the suite
  • Smoke tests and key infrastructure decisions
  • Cross-service flows both covered and not covered
  • Test assertions at the boundary level
Step 08

Review the deployment model

Understanding how an application is deployed — its target platforms, containerization strategy, and infrastructure automation — is essential before you onboard as a contributor or run the application anywhere beyond your laptop.

bob prompt — Ask mode
Analyze the deployment model for this application. Reference @docker-compose.yml, @deployment_scripts, @terraform, @.github/workflows, and the deployment documentation in @docs. Describe the supported deployment targets, how each service is containerized, what infrastructure is provisioned, and how CI/CD is configured.

Bob reads the deployment artifacts and produces a deployment model analysis covering:

  • Supported deployment targets
  • Containerization strategy for each service
  • Infrastructure provisioning details
  • CI/CD workflows
  • Key deployment constraints and gaps
Step 09

Save your findings to the repository

The analysis you produced in Ask mode lives only in the chat session. Switch to Agent mode to ask Bob to write a persistent onboarding reference document to the repository, so future contributors can benefit from this work.

Switch to Agent mode

Select Agent in the mode selector, or type /agent in the chat input field.

Create the onboarding reference

Ask Bob to consolidate everything it discovered into a single Markdown file. Bob has the full context of the conversation and synthesizes findings without re-reading all the files.

bob prompt — Agent mode
Create a file called docs/ONBOARDING.md. Create one section for each of these topics: 1. Application overview: purpose, project structure, high-level architecture, and the main responsibilities of each top-level directory. 2. Tech stack analysis, including a "Stack at a Glance" diagram. 3. Key components and their interactions, including a component interaction map. 4. Unit test coverage analysis. 5. End-to-end test coverage analysis. 6. Deployment model analysis. Populate each section with everything you discovered in this session. Use clear headings, Mermaid diagrams, and tables where appropriate. Keep the tone concise and technical.

Bob writes the file. If auto-approval is disabled, click Approve when Bob requests permission to write docs/ONBOARDING.md.

Verify the output

Open docs/ONBOARDING.md in the editor to confirm the document contains all the expected content. You can also ask Bob to preview it:

bob prompt
Show me a preview of docs/ONBOARDING.md

Bob renders the Markdown in the chat interface. Review the content for accuracy and completeness before committing.

Result

You now have a docs/ONBOARDING.md file that captures the complete application understanding — available to every contributor and to Bob itself in future sessions.

Troubleshooting

Common issues

Bob's analysis is shallow or misses services

By default, Bob reads the project structure and a selection of key files. If the output is missing a service, add an explicit context mention. For example, if the Java hold service is missing from the tech stack analysis:

bob prompt
Analyze the tech stack for @booking_system_inventory_hold_service/pom.xml and add the Java hold service to the tech stack summary you produced earlier.

Bob cannot find test files

bob prompt
Analyze the test coverage in @booking_system_backend/tests and @tests_e2e. List every test file and summarize what each one covers.

/init generates an empty or incorrect AGENTS.md

Confirm that galaxium-travels/ (not a subdirectory) is open as the workspace root. All three service directories must be visible at the top level. If the root lacks a README.md, add one and rerun /init.
