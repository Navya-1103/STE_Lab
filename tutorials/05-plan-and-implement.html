Tutorial 05 · Feature Development

Plan and implement complex features

Use IBM Bob's Plan mode to scope, review, and implement complex features with an AI coding agent. Walk through writing a planning prompt, refining the generated plan, and running implementation in Agent mode.

Overview

Why use Plan mode?

Bob is an autonomous agent. When you use a vague prompt, Bob fills any gaps with its own assumptions — which may not match your intent, even if they are technically accurate.

When you create a plan, Bob generates a set of Markdown files that describe the scope, architecture decisions, and ordered implementation steps. Because the plan is separate from the implementation, you can read it, question it, and refine it before Bob writes any code.

The scenario

In this tutorial, you use Plan mode to create a structured implementation plan for adding a price range filter to the Galaxium Travels flights page — a min/max price slider that narrows the flight list in real time. You then approve the plan and let Bob implement the feature.

Prerequisites

What you need

  • IBM Bob IDE
  • Git to clone the example repository.
Step 01

Set up your environment

bash
git clone https://github.com/Navya-1103/galaxium-travels
  1. In Bob, click File → Open Folder and open the galaxium-travels directory.
  2. Run /init in the Bob chat panel to have Bob create AGENTS.md files.
bob chat
/init

Click Approve todo tools for task to create the files. The root AGENTS.md file tells Bob the project's overall structure, conventions, and goals so Bob can write code that fits your project.

Why /init matters for planning

Without AGENTS.md, Bob starts from scratch every conversation because Bob is stateless. The rule files in .bob are where Bob creates AGENTS.md for each of its modes: Agent, Plan, and Ask. Each mode has a different set of rules that guide Bob's behavior in that mode.

Step 02

How to write a Plan prompt

The prompt you write in Plan mode becomes the specification Bob works from. A vague prompt produces a vague plan. Before you type, answer these four questions:

What does it do?

What does the feature do, and what does it not do? Explicit scope prevents Bob from adding work you did not ask for.

Which layers?

Which layers does the feature touch? For example: UI, API, database. Name them explicitly.

What constraints?

File count limits, naming conventions, backward compatibility requirements — anything Bob should treat as non-negotiable.

What is "done"?

A concrete acceptance criterion, e.g. "a user can drag a min/max price slider and the flight list updates immediately to show only matching flights."

Step 03

Generate the plan

Switch to Plan mode

Open the agentic chat sidebar. Select Plan from the mode selector in the chat interface.

Create the plan

Run the following prompt. Notice how it applies the four scoping principles: it names the exact layer to change (frontend only), sets a file count limit, explicitly excludes backend and database work, and states a clear acceptance criterion. The final line is critical — it tells Bob to stop after writing the plan files and not touch any source code.

bob prompt — Plan mode
I want to add a price range filter to the Galaxium Travels flights page. Users should be able to set a minimum and maximum price to narrow the list of displayed flights in real time. Scope: - Add a min/max price range slider (or two numeric inputs) to the search/filter bar on the Flights page - Filter the displayed flight list in real time as the user adjusts the price range - Show the active price range values next to the control so users can see what range is applied - Do not add any back-end or database changes — all filtering happens on the already-loaded flight data in the browser - Do not change the existing text search behaviour Constraints: - Create a folder called `plans` in the galaxium-travels folder - Do not create more than two plan files - Only modify files inside booking_system_frontend/src — do not touch any other directory - Match the existing glass-card and cosmic visual style of the Flights page Done when: A user can set a min and max price on the Flights page and the flight list immediately updates to show only flights whose price falls within the selected range. Important: Write the plan Markdown files only. Do not write, modify, or create any application source code. Stop after the plan files are saved and wait for further instructions.

Bob may ask clarifying questions about your intent. Answer them, or tell Bob to select the best options. Click Approve skill tools for task and Approve subagent tools for task when prompted.

When Bob finishes, it requests approval to write the plan files. Click Approve edit tools for task. Bob places the plan files in the plans/ folder as Markdown files — no application source code is written at this stage.

Plan mode only writes plans

At the end of this step you will have one or two .md files inside plans/. No TypeScript, no CSS, no component files — those come later, only after you have reviewed and approved the plan in Steps 04 and 05.

Step 04

Review the plan

The plan files are the specification Bob builds from. Open the files in plans/ and review them carefully.

When reviewing plans, look for:

  • Scope match: Does the plan include everything you asked for? Does it include anything you did not ask for?
  • Vague language: Look for phrases like "add as needed" or "update appropriately." These are unstated assumptions. Replace them with specific instructions before approving.
  • Named files: Each step should identify the files it touches. If a step says "update the booking component" without naming the file, ask Bob to be more specific.
Step 05

Iterate on the plan

If the plan does not match your intent, ask Bob to revise it in the same Plan mode conversation. You do not need to start over.

For example, if the plan Bob generated left the default price range unspecified, or did not describe what happens when no flights match the filter:

bob prompt — Plan mode (same conversation)
Please update the plan with the following details: - The default min price should be 0 and the default max price should be the highest price in the loaded flight list - When no flights match the active price range, show the same "No flights found" empty state that already exists for the text search - The active price range values should be displayed in Galaxium Credits (e.g. "500,000 – 2,000,000 credits")

Review the plan again after revisions. Repeat until you are satisfied that the plan matches your intent exactly.

Do not skip this step

The plan is your opportunity to catch issues before Bob writes any code. A 5-minute review now can save 30 minutes of undoing changes later. Implementation does not start until you explicitly run the Build the features in the plans folder @plans/ command in Step 06.

Step 06

Implement the feature

Only run this step after Steps 04 and 05 are complete

Do not run the implementation prompt until you have reviewed the plan (Step 04) and iterated on it until it matches your intent (Step 05). The command below is the trigger that starts code generation — nothing in Steps 03–05 writes any application source code.

Start a new conversation

Click the + at the top of the chat interface to start a new conversation and clear the context window. Starting a new conversation:

  • Prevents earlier planning discussion from consuming your token budget.
  • Keeps the implementation context focused on the approved plan.
  • Reduces the risk of Bob conflating planning and implementation instructions.

Switch to Agent mode

Select Agent from the mode selector to switch to Agent mode.

Build the feature

Submit this prompt to implement the feature. The @plans/ reference passes all plan files as context, so Bob builds exactly what is described in the approved plan — nothing more.

bob prompt — Agent mode
Build the features in the plans folder @plans/

Bob prompts you to Approve todo tools for task and Approve edit tools for task. Approve both requests.

Result

You have added a real-time price range filter to the Flights page — purely in the frontend, exactly as scoped. The flight list narrows immediately as the user adjusts the range, showing prices in Galaxium Credits with a clear empty state when no flights match.

Step 07

Run the application with the new feature

After Bob finishes implementing the price filter, use the start script to launch both the backend and frontend together. The script handles dependency installation automatically.

macOS — run start.sh

Open a terminal in the galaxium-travels root directory and run:

bash — macOS
chmod +x start.sh && ./start.sh

Windows — run start.bat

Open a Command Prompt in the galaxium-travels root directory and run:

cmd — Windows
start.bat

Both scripts start the Python backend on http://localhost:8080 and the Vite frontend on http://localhost:5173. Open http://localhost:5173 in your browser once both servers are running. Press Ctrl+C to stop all servers.

What the script does

The start script checks for Python 3 and Node.js, creates and activates a Python virtual environment if one does not exist, installs backend and frontend dependencies on first run, then starts both servers in the background.

Verify the price filter feature

  • Navigate to the Flights page and confirm the price range filter control is visible in the search bar alongside the existing text search.
  • Adjust the minimum price upward — confirm that cheap flights disappear from the list immediately.
  • Set a very low maximum price so no flights qualify — confirm the "No flights found" empty state is displayed.
  • Reset the range to its defaults — confirm all flights reappear.
  • Confirm the displayed price range is shown in Galaxium Credits format (e.g. 500,000 – 2,000,000 credits).
Done

The price range filter is live. Users can narrow the Galaxium Travels flight list by min and max price entirely in the browser — no backend changes, no database migration, exactly as scoped in the plan.

Business Value

Traditional approach vs. IBM Bob

Complex features touching multiple layers — UI, API, and database — require careful coordination. Without a structured plan, assumptions accumulate and rework is expensive.

Traditional approach
  • Developer writes a feature branch directly from a ticket with minimal specification
  • Scope creep and missed layers discovered during code review — costly to unwind
  • Design discussions happen in Slack threads or meetings — context lost, not version-controlled
  • Cross-layer coordination (UI + API + DB) relies on verbal handoffs between specialists
1–2 days of back-and-forth before code is even written
With IBM Bob
  • Plan mode generates a precise, reviewable spec in minutes from a structured prompt
  • Every layer (UI, API, DB) is named explicitly in the plan before a single line is written
  • Plans are Markdown files committed to the repo — reviewable, diffable, and traceable
  • Agent mode implements from the approved plan in a clean context, keeping scope tight
Under 1 hour from prompt to working feature
Time saved: 1–2 days of planning overhead and rework per complex feature. The plan is the spec — review it before any code is written, not after.
